How it works

Every tool here follows the same pattern. Nothing an agent receives or produces is trusted because of where it came from. It is checked first, against rules you can read, and either acted on or refused with the reason.

The tests behind each tool are themselves tested: a mutation gate breaks the code on purpose, one small change at a time, and the build fails unless the tests catch every break. GitHub re-runs that gate on every change, so the green is not our word.

That the tests are real

The mutation gate, witness, is itself public and MIT-licensed. GitHub’s machines run it on every change to every tool here, and the run logs are public (each tool’s “Test runs” link below), so the green is GitHub’s record, not our word.

Run it yourself. With git and Node 22 installed, this re-runs this page’s own gate on your machine:

git clone --depth 1 --branch v0.6 https://github.com/sjgant80-hub/witness.git
git clone --depth 1 https://github.com/sjgant80-hub/sovereign-ai-security.git
cd sovereign-ai-security
node --test kernel.test.mjs guarded.test.mjs page-parity.test.mjs
node ../witness/witness.mjs mutate kernel.mjs --test node --test kernel.test.mjs

The last line breaks the map’s code on purpose, one change at a time, and reports how many breaks the tests caught. Every one must be caught, or the gate fails. The rules we work by

These are not small print. They are what a regulated buyer checks first, and they are why the tools are safe to run inside your walls.

  • Defensive first. We build tools that protect systems. That is the whole catalogue above.
  • Scope and authorization on every testing tool. Anything that tests an attack runs only against your own systems, or a target you have authorized in writing. When those tools ship, each will refuse to run without a recorded authorization and target scope, and will print that scope on every result.
  • Responsible disclosure. If we find a weakness in someone else’s software, the maintainer hears first, privately, before any public write-up.
  • No tools for defeating AI safety. Nothing we supply, to anyone, is built to get around an AI system’s safety measures. Our red-team work tests only your own systems, with your written permission, and what it finds goes to you. Trust is what you are buying; we will not sell the opposite.
  • Sovereign by architecture. The checks are code that runs on your device — in your browser, or on servers you run — so there is nowhere for your data to be sent. You can watch that, and lock it: see Check it yourself.
  • Proven, not trusted. Claims are checked before they are made, the checks are re-run on independent machines, and what failed stays on the record.

Why a security product should be provable

Agents created a new attack surface faster than the tools to defend it. The common answer is another model, asked to judge whether the first one is behaving. That moves the problem rather than solving it: now you must trust the judge.

The answer here is older and plainer. Verify before you trust: check the signature before you parse the message, the capability before you act, the characters before the agent reads them, the tests before you merge. Make each check deterministic, so the same input always gives the same verdict. Run it on your own hardware, so nothing sensitive travels. Then prove the checks themselves — break the code on purpose and require the tests to notice — and publish the record, failures included.

None of this makes an organisation safe on its own. It makes the safety claims checkable, which is the thing a regulated buyer has never been able to get from an AI vendor.
